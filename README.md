# AgentFlow Pay

通过对话把目标整理成可编辑任务图，也可以从模板开始。生成时就关联已接入服务并检查成果依赖；确认任务图后直接获取服务报价，再选择方案、托管预算，按任务就绪情况委派，验收后结算。当前可执行业务为销售分析和旅游规划；其他领域可以保存设计，未接入的能力会明确说明。

## 日常启动与操作

已经安装依赖时，双击根目录 `start-demo.cmd`。启动器先构建更新后的页面，再重启本项目服务；保留本地链、历史项目和资金记录。窗口按 **R** 重启、**Q** 或 **Ctrl+C** 停止。网页要求登录时，在启动窗口按 **C** 复制被掩码显示的登录令牌，然后粘贴到网页。令牌每次登录成功后自动更新，下次登录需重新复制。

1. **与 AI 讨论目标**：默认进入“项目与成果”的总任务列表，点“新建任务”后描述想完成什么，不必先选择业务类型。首次规划读取当前服务目录，按真实输入输出组织业务节点：独立检索可并行，后续任务只等待它实际需要的成果。平台的需求确认、边界判断、预算校核和验收不会单列为业务服务。已接入的节点保留服务关联，生成时先用执行规则检查依赖；未知业务仍可保存设计，但会说明执行能力缺口。
2. **先看粗略 DAG**：只需说明大致方向，默认直接生成可修改的草稿，预算、日期、规模等未知条件可以留作待补。如果明确只想讨论，会保留讨论入口；随时可以点“先生成草稿 DAG”。不需要先满足全部需求、补完资料或学会专业术语。
3. **编辑和确认 DAG**：图默认适配当前画框，切换页面或调整窗口后重新定位；也可点“定位全部任务”或“放大查看 DAG”。节点编辑表单直接显示，点击图中节点切换编辑对象，可修改内容、输入输出、验收和依赖，也可增删任务。不再重复展示整排节点按钮和第二份交付清单。确认任务图后图与编辑区保持显示，报价入口紧接其后。未关联的需求、未完善的验收、未接入服务等仅作后续建议，不阻止保存或确认当前规划版本。程序仍防止循环、丢失依赖和非法引用。“确认这版任务图”直接保存客户认可的不可变版本，不调用模型批准；“AI 查漏（可选）”单独提出建议，失败也不影响确认。之后可继续修改，旧确认版本保留。
4. **使用模板库**：左侧“工作区”新增独立“模板库”，搜索、预览并按模板直接复制 DAG；此操作不调用模型。包含产品上线、活动策划、学习路线及原有服务模板。自己的任务图可通过“保存为可复用模板”加入库，下次继续修改。
5. **继续已有方案**：“项目与成果”按每次总任务列出名称、时间、工作数量和状态，点任务继续执行或验收；尚未发起的对话方案在“未发起的方案”中继续编辑。支持导出当前 DAG 或指定确认版本的 JSON。切换模板库或其他页面会保留当前未保存编辑。

通用规划借鉴 [MapFlow](https://github.com/rongyan-123/MapFlow) 公开生成技能中的渐进澄清、主干确认、按可验收成果拆解与迭代审查。公开仓库列出的核心后端和生成引擎在另外的工程；本项目使用自己的 Python 后端与现有模型接口实现，并未照搬未公开的服务端。

保存或确认任务图不会收费。确认后自动定位到图下方的“服务报价与预算”，设置 Agent 服务费上限，点击“获取服务报价”。报价前由程序检查材料、服务在线状态和任务输入，无需再让模型拆一遍；整个过程不会托管资金，选择方案并确认托管才创建付费任务。旅游仅显示出游条件，销售仅显示销售材料和统计设置，已识别条件直接带入。任何节点的执行能力未注册或已移除时，整张 DAG 保留为“规划预览、未落地”，不能发现服务、报价、执行或托管结算；接入能力并更新任务图后才能继续。已注册能力的服务暂时离线则显示服务不可用。图、材料、参数或预算变化后旧报价失效。旧的无服务绑定草稿可点击“按已有需求重新生成任务图”，原确认版本保留。现有引擎限制单场景、最多 16 节点，重复能力组合暂不支持。销售仍需私有 CSV，旅游无需上传 JSON；资料来源由系统标明，普通用户不用指定“演示资料”。页面发现后台仍在运行旧版本时，会提示在启动窗口按 R 重启并刷新。

### 服务共同规划与按需协作

“项目与成果”的模型规划改为按服务分工：入口角色只整理目标、补问条件并找到负责最终成果的服务；该服务提出自己的工作和需要的前置成果，再由所需服务分别提出提案。程序按照这些请求组装任务图，相同能力只规划一次，互不依赖的服务并行。例如完整旅行方案由报告服务请求行程，行程服务请求景点和住宿；只要景点时只规划景点服务。每个角色仍共用 `planner.local.json`，无需增加配置。图下显示各服务提出的协作需求。

规划角色由平台运行，不会在托管前向每一家商家派付费任务。服务输入契约漏写时，程序补齐并在 `graph.collaboration.participants[].requests[].source` 标为 `service_contract`；模型提出的请求标为 `service_role`。缺失服务保留为能力缺口。确认后沿用原有完整帕累托方案、预算授权、服务发现、报价、托管和就绪委派。历史任务和模板不迁移，不改现有合约。旧 `/planning` 兼容入口保留原实现；新的协作规划入口是 `/designs`。

执行时，模型可以把收到的消息编号放进 `execute_task.useMessages`，明确采用消息中的 `data.parameters`，也可自己填写 `parameters`。路线工具已支持选择候选酒店（`hotel_id`）、安排景点优先顺序（`attraction_order`）和排除景点（`exclude_attraction_ids`）。这些选择会进入真实计算，改变行程和最终报告；用户日期、人数、预算及来源价格保持原值。不支持的调整会说明原因，不能仅回复“已修改”。其他业务工具仍按已有参数计算，尚未支持任意业务调整。

执行反馈带有本订单的任务目录和多层前置成果目录。需要更早的依据时，服务向 `platform` 请求 `data={key: "evidence", taskKey: "hotels", names: ["hotels.json"]}`，平台返回原文件、来源节点、轮次和成果哈希；大文件分页读取。同一文件在模型上下文中只展开一次，重复项保留引用，不改原文件或金额。向正在工作的服务询问解释时可加 `data.responseMode="explain"`，问题会进入对方收件箱，不用已有候选文件替代答复。已结算服务仍只提供存档成果。

这里分散的是规划和执行决定；消息转交、订单记录和支付仍由平台统一协调。没有引入大小模型路由，也没有实现完全去中心化网络。旅游继续查询带来源的演示资料库，没有新增实时查询或预订能力。

回归命令：`python -m pytest tests/integration/test_cooperative_planning.py tests/integration/test_cooperative_execution.py`；完整流程用项目虚拟环境运行 `python tests/e2e/run_cooperative_workflow.py`。后者启动独立测试链、服务和脚本化模型接口，经过实际业务文件生成、人工验收接口、结算和退款，并在 `experiments/raw/cooperative/` 保存证据；它验证协议与流程，不代表真实模型推理效果。

### 执行中的服务通信

新订单使用执行会话：服务可以报告进度、提出问题或调整请求、提交中间成果、接收反馈，再继续同一个任务。任务详情的“执行沟通”显示真实消息；确实需要用户补充时，页面直接提供回答框。已有资料由平台直接提供，普通任务不强行制造问答。原商家比较、就绪后选人、托管预算、DAG 依赖、人工验收与退款保持不变。

消息通过已有 A2A 1.0 JSON-RPC 任务传输。平台转交同项目有效委派之间的请求：接收方收到实际上下文和消息后，由自己的执行程序决定如何回答、是否调用工具、怎样调整未完成工作。平台不预设景点/酒店或报告/统计的对话配对。未接单的服务不会为通信提前派单；已结算服务的成果由平台直接提供，修改或追加付费工作返回“需要重新授权”，不会免费重做或改写旧成果。

候选稿不付款。完整候选先按已确认要求检查，不合格时把具体问题退回原服务；服务可修正后重新提交。正式交付必须对应最近检查通过的候选，随后仍走独立验证、必要的人工验收和原链上结算。待回答的问题未处理完，不能直接宣布任务完成。通信不改变价格、交付范围、依赖、截止时间或收款人。

每个参与者有独立的持久化状态和收件箱。双方同时等待时仍可处理收到的请求，其他任务继续执行。消息绑定链、合约、订单、节点、委派轮次、执行会话和顺序号，并验证发送方签名；旧执行者的消息不能进入新会话。请求在发送前、服务结果与状态在返回前保存，断线查询和恢复原 A2A 任务，已保存的轮次不重复运行。每个会话最多 48 轮、3 次完整候选；每次委派最多 6 个补充请求，报告返工不重置请求额度。连接最多尝试 3 次，等待不超过原执行期限，并预留验证与结算时间。

#### 接入自己的执行智能体

通道、转交和恢复位于 `services/orchestrator/sessions.py`；服务接入接口位于 `services/agents/session.py`。新订单节点冻结 `options.communication = "execution-session-v2"`，报价发现只接受相应能力上声明 `agentflow:execution-session-v2` 的服务。合作方可以直接通过已有托管适配器接入：

```python
from services.orchestrator.application import agent_app

# MyWorker 是服务商自己的执行循环，可以调用自己的模型或业务工具。
api = agent_app(config, deployment, runtime, token, worker=MyWorker())
```

`MyWorker` 实现异步 `advance(context)`，返回 `(Action, state)`。`context` 包含本次任务、冻结的输入、平台反馈、收到的消息及上轮状态。`context.produce()` 调用现有真实业务工具；`context.deliver(artifacts)` 为服务自行计算的文件建立实际交付及签名，不能绕过后续客观验证。`state` 保存中间结果、工具调用进度和已处理消息，不使用全局变量混合多个订单。

`Action` 支持 `progress`、`request`、`reply`、`candidate`、`final`、`failure`、`wait`。请求指定目标节点的 `key`（或 `platform`、`user`）、用途 `information` / `adjustment`、具体说明和必要数据；答复引用收到的消息 ID，明确答复、接受或拒绝。部分候选放在 `data`，完整候选放在 `delivery`。只有 `final` 的正式交付能进入结算流程。文件较大时传成果引用，不把整个资料库塞进消息；消息数据最多 64 KiB。平台对自然语言不作隐含授权，接入方必须把调整落到约定范围内的实际工具调用和新成果上。

主智能体和本项目启动的子智能体现在共用根目录 `planner.local.json`，不需要为每个子智能体重复配置地址、模型或密钥。配置可用时，新执行会话自动使用 `services/agents/model_worker.py`：模型读取本节点任务、材料摘要、已有成果和消息，选择调用业务工具、读取文件、请求补充、答复其他 Agent、提交候选或正式交付。不同任务各自保存工作状态，模型配置不写入会话记录。保存配置后新会话自动读取；模型会话中配置失效、请求失败或返回非法操作会明确失败，不会悄悄改用固定程序冒充模型执行。模型调用与工具执行受原任务截止时间约束，不自动延长已授权委托。

尚未配置模型时，原有模板及确定性业务工具仍可演示；已开始的内置工具会话保持原模式。配置模型后，子智能体使用同一接口自主选择下一步，但实际工作仍由已接入的业务工具完成：清洗、验证、统计、演示旅游检索、路线和报告。模型不能凭一段文字伪造文件；候选和正式交付引用实际工具成果，最终仍按原规则核验。工具错误、收到的答复和候选检查反馈会进入下一次模型调用。当前工具遵循确认过的输入、参数和交付要求，不支持任意代码或新增业务；修改这些要求仍需调整方案。旅游继续使用标注来源的演示目录，没有接入实时查询、预订或购票。

接口：`GET /api/jobs/{jobId}/collaboration` 查看消息；`GET /api/jobs/{jobId}/communication/requests` 查看当前需要用户回答的问题；`POST /api/jobs/{jobId}/communication/requests/{requestId}/reply` 提交 `{"message":"补充说明"}`。这些接口沿用工作区认证，回答不能修改预算或替换冻结材料。旧版本通信只为已有委托和历史记录保留兼容，新订单不再自动触发固定的“质量依据/路线依据”问答。运行数据、已结算成果和合约不清理、不重置。

## 首次安装与启动

支持 Windows / Linux x64。先安装 Python 3.12 和 Git：

```shell
git clone --branch A --single-branch https://github.com/yutun005/CCFblock_chain.git
cd CCFblock_chain
python manage.py setup
python manage.py dev
```

Linux 如无 `python` 命令，使用 `python3`。上述命令直接取得 A 分支的当前版本。`setup` 安装锁定的 Python/前端依赖、Foundry 和 Solidity 依赖，并编译合约与前端。若当前环境找不到 Node/pnpm，会下载已校验的 Node.js 24.19.0 和 pnpm 11.25.0 到项目 `.cache/tools/web`，不需要全局安装，也不依赖编辑器的环境。首次安装需访问 nodejs.org、PyPI、npm、GitHub 和 Solidity 编译器下载源；依赖放在本项目的 `.cache`、`node_modules`、`contracts/lib` 中。

双击启动时，如页面源码有更新，会先补齐前端依赖并构建页面，成功后才停止旧服务、载入当前版本。下载或构建失败会保留旧服务，原因显示在启动窗口中；联网后再次双击即可重试。工具已下载且依赖未变时不会重复下载安装。

打开启动器打印的 **Open http://127.0.0.1:端口**，在启动窗口按 **C** 复制登录令牌并粘贴到页面；每次登录成功后令牌自动更新。初次启动会避开被系统保留或占用的端口。Windows 已安装依赖后也可双击 `start-demo.cmd`。启动器首次生成隔离本地账户、部署合约并启动市场、验证器、16 个 Agent 和 Web/API；无需复制开发者的密钥或本地链数据库。

网页可预览计划与预算、创建任务、观察 DAG/SSE 状态、下载成果、领取报酬和退款。Ctrl+C 停止服务；`python scripts/local_demo.py stop-chain` 停止本项目的 Anvil。

已安装依赖时，在 PyCharm 打开项目根目录，把解释器设为本项目 `.cache/venv/Scripts/python.exe`（Linux 为 `.cache/venv/bin/python`），运行 `manage.py`，参数填写 `dev`，工作目录选择项目根目录即可。运行窗口保持打开，浏览器按打印地址访问。费用使用本地测试代币。

## 已接入业务的执行与成果确认

统一从“项目与成果”完成整次任务，侧栏不再保留“执行与验收”和“协作任务”两套重复入口。

1. **提出目标并确认任务图**：点击“新建任务”，与规划助手对话，或从“模板库”复制方案。节点编辑区始终显示。确认前只保存设计；确认后才出现服务报价和预算设置。
2. **补充材料并选方案**：销售分析选择或上传自己的 CSV；旅游条件从对话带入，不要求用户准备景点或酒店 JSON。点击“获取服务报价”，展示全部帕累托前沿方案，无前三名数量限制。选中的卡片变浅色并标明“已选择”。服务明细、预算上限和确认按钮直接显示；点击“确认并托管服务预算”才发起付费任务。
3. **执行与沟通**：托管后进入当前任务详情。任务图显示进度，各步骤就绪时自动选服务并执行。“执行沟通”按步骤显示进展、成果和待回答的问题；报价细节、轮次和时间线收在“报价与执行记录”中直接显示，点图中节点会定位到对应详情。用户不需要切换到另一个执行页面。
4. **报告验收**：报告生成后，在当前任务顶部阅读全文或下载原文件。验收后重新验证成果；本地链空闲时按下一次出块时间计算证明有效期，证明过期导致结算回滚时会在委派仍有效的情况下自动重试一次。可“验收通过并结算”“退回修改”或“不通过”。退回时填写位置和意见，新稿生成后再次验收；历史稿可对照，只有最新稿可验收。最多两次免费修改。拒绝后不结算报告，已完成的前置工作费用保留，未使用余额可领取。期限结束不会自动接受。
5. **结算和退款**：验收成功后进入“任务结算”，等待链上结果更新费用。任务结束有余额时点“领取退还代币”；交易确认后显示到账金额并禁用重复领取。退款不依赖商家在线或商家提现。页面保留各项实际服务费用，链上交易记录直接显示。
6. **查看历史成果**：侧栏“任务成果”以每次总任务为列表元素，同一项目的多次执行各有一条。点开后直接显示最终报告、验收记录和该次任务的中间成果。已在验收区展示的报告不会再生成一份重复文件卡片。其余最终交付按确认的交付范围归类，旧任务没有范围记录时按末端节点归类。所有文件仍可下载，任务结算也可从这里打开。

任务列表只读取现有记录，不迁移、删除或重建历史任务。原增量版本、复用计算和材料接口继续保留；本次主页面统一为对话方案入口，原独立材料表单、重复模板入口和旧续单表单不再单独挂在菜单上。现有草稿的未保存编辑在页面切换时保留；已发起任务在列表中直接打开。服务定义和商家维护集中到“服务市场”，在线服务实例始终显示。每张卡片的“查看详情”打开弹窗，在弹窗中查看服务信息、修改资料或删除；保存失败保留填写内容，可重试，关闭弹窗返回原卡片。全站需求说明、任务图、服务报价、执行记录、成果、验收与链上记录均直接显示，不使用箭头折叠。

交付中的材料和节点配置已冻结，追加材料、指标、天数或另一语言的完整报告需要续单重新确认。系统不会把未支持的分析或翻译要求当作已实现能力；当前返工采用上述确定性修改方式。新任务使用 `execution.dispatch=on_ready`：前置任务结算且结果可读取后才询价，按已确认偏好选择当前空闲商家。每步及整单预算不增加；失败后仍按原恢复规则重新询价，实际执行者与签名成交价保留在任务记录中。旧的已托管计划保留原签名与执行偏好。

本工作区对同一钱包实行一个未完成委托的容量限制，覆盖不同技能和不同项目；委派确认与占用检查串行完成，其他商家可以并行执行。只有忙碌候选时等待并刷新报价，不消耗执行次数；仍受整单截止时间约束。占用由链上任务和持久化交易记录恢复，重启不会误把正在执行的商家当成空闲。委托包含结果验收与原执行者返工，结算、取消或到期后释放占用。当前不统计其他平台的商家负载，也不宣称获得全局最短工期。

方案预估中，每项服务取最近最多 50 次履约的成功比例。优先使用本工作区与链上已确认任务匹配的记录；没有链上记录时使用商家语料，分别标明“演示数据”或“人工录入”。无记录的商家仍可接单，不把未知成功率当作零或百分之百。整单参考成功率取各步骤比例的乘积，这是独立性假设下的估算。总费用按参考商家的签名估价相加，总耗时按依赖就绪与同商家串行限制模拟，不包含其他项目占用、重试、链上和人工确认时间；实际选人变化后预估也可能变化。运行时按最新签名报价、申报耗时及链上履约记录重新排名，未知履约使用明确的平滑评分，不作为已知成功率展示。精确比较最多 100000 种候选组合，超出时明确报错，不把部分搜索结果冒充完整前沿。

旅游需求通过 `/api/workspace/travel/prepare` 澄清；内部生成的 `travel-request.json` 只包含结构化需求与资料库版本，不包含景点/酒店清单。两个检索 Agent 在执行时独立读取并筛选该版本的资料，验证器重新核验候选，路线和报告继续沿用链上已验证的前置成果。没有候选、资料版本不符、行程不可行或服务不可用时明确失败，不伪造成功结果。资料库版本绑定在冻结输入中。新任务使用 `data/travel/demo-catalog-v2.json`，覆盖示例城、杭州、北京、上海、成都、西安；地点、价格、交通和房态均为合成演示数据。原 v1 保留供已绑定的任务读取；未来更新资料应另建版本，不能替换在途任务的数据依据。

原旅游 JSON 材料接口继续兼容历史资料；普通旅游入口直接使用出游需求，既有任务、历史和资金状态继续使用原协议。销售数据仍属于用户必须提供的私有材料。未接入执行与验收适配器的新能力不能通过给节点改名实现，需先接入对应服务。

## 服务业务图与商家管理

打开“服务市场”，点击服务节点即可查看所有关联商家、费用、预计耗时和近期成功率。初始 `data/service-corpus.json` 包含 16 个演示商家、8 类服务、32 个商家服务关联和 1600 次模拟履约记录；这些数据用于初始化竞争市场，不是真实商业履约证明。初次启动会启动相应的 16 个独立服务；旧本地环境重启时补齐商家账户，保留原链与项目历史，有未完成任务时提示先处理。

点击“新增商家”填写标识、名称及提供的服务；每项服务分别填写费用、耗时、近期统计次数和成功次数。点击现有商家的“修改商家和服务”可增删服务关联。点击“新增服务定义”填写名称、检索词、场景和输入输出契约，再关联商家；导入商家数据时遇到未有的服务标识也会自动建立待完善节点。商家资料标识与在线注册的 Agent ID 对应，只有通过原有钱包与接口注册校验的在线商家才能接单。填写资料不会伪造接口或签名。

可通过“批量导入 / 导出语料”下载 JSON 格式示例、编辑后追加导入。只更新列出的对象；未列出的对象保留。资料在运行数据库持久化，重启后继续保留。输入输出相容的服务间建立前置成果边，主 Agent 检索会带上必要前置服务；不允许把图外技能分配出去。新业务可入图，实际执行仍须接入对应的执行器和独立验收契约，页面明确标记待接入状态。

服务、商家和两者关联均可删除。服务删除后节点与相关边移除；商家删除后移除其全部服务关联，服务没有剩余商家时保留能力节点并标明尚无可接入提供者。删除状态不会被注册心跳复活，恢复需要显式勾选。已经执行的任务与成果不删除；未付款方案遇到服务库变更会要求重新比较，防止按照过期商家或服务发起托管。更新与删除检查 `revision`，冲突时刷新后重试。


新增接口统一位于 `/api/workspace/`：`planner`（配置状态）、`planning`（提出并校验任务图）、`planning/{id}`（规划记录）、`planning/{id}/review`（用户校验并冻结新副本）、`capabilities`（来自业务图）、`service-graph`（检索与图）、`service-corpus`（读取/追加更新）、`service-graph/{service|merchant}/{id}/delete`、`templates`（检索/创建）、`templates/{id}`（查看）及其 `apply`/`update`/`delete` 操作、`materials`、`parse`（手动模式关键词解析）、`comparisons`（共享估价后去重）、`proposals`（单方案）、`confirm`、`projects`、`versions/{id}`、`reviews/{jobId}`、`drafts/{resultHash}`；对 `reviews/{reviewId}` 提交 `accept`、`revise` 或 `reject`。确认方案需提供原预览的 `confirmationHash`；报告决定需提供最新 `resultHash` 和唯一 `decisionId`。全部沿用工作区认证令牌，仅面向当前单管理员工作区。模板更新和删除须提供当前 `revision`，过期操作返回 409；未确认的任务图无法生成报价。

模型子任务调用业务工具生成文件后，程序自动提交完整成果供检查，通过后自动正式交付；不再要求模型额外返回“提交候选”“正式交付”的固定格式。有待回答的问题或实际成果不合格时，仍交回原智能体处理。报告须由用户验收才结算。模型操作兼容常见包装、单项列表及字段别名；真实文件未生成时不会把一句“完成”当作交付。下游任务读取已验证的上游成果，再生成最终报告。

## 通用规划后端

模型返回先经过格式适配，再校验任务图。普通聊天只需回复内容，不要求重复整套需求和 DAG；生成任务图可只返回任务名称、编号及依赖，程序补齐可编辑的阶段和待完善字段。兼容常见 JSON 包装、代码块、节点/连线表示及字段别名；更新时省略的既有任务字段会保留。格式适配仅用于模型响应，手工编辑接口仍校验原有契约，循环和不存在的依赖不会被静默忽略。解析失败只记录字段位置及错误类型，不记录用户对话或密钥。

新增 `/api/workspace/designs` 创建/列出对话方案，`designs/{id}` 读取；其 `messages`、`expand`、`edit`、`confirm` 分别继续对话、确认主干展开、保存手工图和确认最终版。变更携带 `expectedRevision`，过期修改返回 409。`designs/{id}/versions/{versionId}` 读取不可变版本；`designs/{id}/template` 保存个人模板。`/api/workspace/design-templates` 列出模板，`design-templates/{id}/apply` 携带模板 `revision` 复制任务图。

方案、确认快照、个人模板分别持久化于 `design_sessions`、`design_versions`、`design_templates`，与已执行项目分开，统一沿用现有工作区令牌。程序校验图结构、阶段及输出引用；需求覆盖、验收完整度和最终成果关联不足只提示后续完善。模型查漏是可选建议，不能代替客户决定是否确认当前草稿。模型响应不合法时最多修正一次，失败不覆盖已保存方案。无论是否配置模型，最终确认都由用户决定并记录当前待补事项；模板直接复制、编辑和确认均不调用模型。可选 `/designs/{id}/review` 使用独立的审查提示词和响应结构，错误格式不会作为审查通过，也不会阻止确认版本。

## 接入规划模型

启动方式保持不变。仓库提供不含密钥的 `planner.example.json`。首次拉取后，在项目根目录把它复制为 `planner.local.json`，填写模型接口地址、模型名和密钥；这一个文件同时供主智能体与本项目所有子智能体使用，无需逐个设置。示例使用 DeepSeek，也可更换提供商的完整 Chat Completions 地址和模型名。已有本地配置时直接保留，不要覆盖。Windows PowerShell 可执行 `Copy-Item planner.example.json planner.local.json`，Linux 可执行 `cp planner.example.json planner.local.json`。

`planner.local.json` 已从 Git 和 Docker 构建上下文排除，不要提交或分享。填好后双击 `start-demo.cmd`，在页面点“重新检查模型配置”，再提交目标、确认方案和服务预算；子智能体接到任务后自动使用同一模型，通过“执行沟通”查看进度并回答必要问题。没有第二份子智能体模型配置。修改配置后无需重新部署合约；若服务尚未加载新版代码，在启动窗口按 R 重启后刷新网页。未配置时仍可使用模板、手工编辑与内置工具演示。例如：

```json
{
  "endpoint": "https://你的提供商/v1/chat/completions",
  "model": "你的模型名",
  "apiKey": "你的密钥",
  "responseFormat": "json_object",
  "tokenParameter": "max_tokens",
  "maxTokens": 8192,
  "timeoutSeconds": 600
}
```

本地兼容服务可用 `http://127.0.0.1:端口/v1/chat/completions`，不需要鉴权时省略密钥。也可通过 `AGENTFLOW_PLANNER_URL`、`AGENTFLOW_PLANNER_MODEL`、`AGENTFLOW_PLANNER_API_KEY` 提供配置。模型若只支持 `max_completion_tokens`，修改 `tokenParameter`；不支持 JSON 模式时将 `responseFormat` 设为 `text`，模型仍须返回符合 Schema 的 JSON。

模型单次调用默认最多等待 10 分钟，可将 `timeoutSeconds` 调到 1800（30 分钟）。已有短配置仍可读取，实际等待至少 600 秒。新建任务每次委派的执行窗口放宽到 1 小时，整单时间包含重试余量；页面上的预计秒数仅供比较，不会据此取消任务。手动创建任务默认也使用 1 小时。已托管订单沿用创建时的期限，更新代码不会改写历史订单。

接口格式参照 [Chat Completions 官方接口](https://developers.openai.com/api/reference/resources/chat/subresources/completions/methods/create)。使用能返回 JSON 文本的兼容接口即可，不要求提供商实现原生工具调用。协作规划给入口角色发送用户对话与需求，给专业角色发送自己的服务契约及协作请求；子智能体执行时向同一接口发送本节点业务上下文、输入/成果的有限文本预览、收到的消息及工具结果，必要时分段读取对应文件。不会发送钱包密钥或付款签名。外部模型调用费用由配置的提供商另行计费，不计入 Agent 服务费托管。同一配置可能同时收到多个子智能体的请求；接口限流或断连会显示具体失败，沿用任务恢复机制。

兼容的原规划接口中，主 Agent 先按目标检索业务图及前置服务，再由模型提出 DAG，系统检查输出 Schema、在线技能、验证策略、依赖类型、环、缺失输入、交付覆盖和多余工作；非法输出最多要求修正一次，仍不合法则拒绝。校验通过的图先交给用户检查和微调；用户明确确认后冻结独立副本，报价时沿用这张图，仅对已结算成果进行复用和移除无需重做的节点；不会再从四节点模板重建。预算上限由用户给定，具体节点费用以服务估价和签名报价为准。模型不能执行工具、选取私钥、签署交易或批准付款；原 DASC 验证及人工确认仍负责结算条件。

已有业务的模型规划先读取当前场景的完整可执行目录，避免按目标关键词检索时遗漏必要能力。需求分析、DAG 生成和语义复核使用同一配置的独立请求，不需要多个模型或训练。补问与修改会增加模型请求；尚无密钥时不会调用外部模型。程序核对交付、排除项、统计参数、出行参数、能力引用和图结构；模型辅助检查原意遗漏和未经确认的替换，模型复核不构成正确性保证，最终仍由用户核对。没有新增地图、天气、预订或分析能力。

需求草案通过 `/api/workspace/planning/intake` 创建或续接，传入 `recipe`，续接时另传 `previousId`、按问题编号填写的 `answers` 或 `feedback`。服务端保存原目标、材料摘要、逐轮问答、能力目录版本和需求哈希。对 `/planning/intake/{id}/confirm` 提交 `specHash` 后生成不可变确认副本，再将返回的 `confirmedRecipe` 和 `intakeId` 提交至原 `/planning` 接口。未确认、材料变化、参数冲突或能力目录版本变化均拒绝继续。最终任务图确认仍使用原 `/planning/{id}/review`，复核后冻结独立副本，修改节点说明不会绕过检查。旧模板与历史任务保持兼容；新的模型规划不能跳过需求确认直接调用原接口。

实际执行范围仍限于注册技能和客观验证规则；通用规划的领域不受此限制。当前没有真实旅游数据接口、天气查询、酒店预订、已有酒店中间结果导入、步行距离规划或销售预测能力；涉及这些要求应澄清或拒绝，不能用文字报告假装完成。规划层的自然语言理解需要在接入实际模型后验收；模拟接口仅能验证协议、拒绝非法规划和执行闭环，不能作为真实模型推理效果的证据。

本轮使用新增 `createReviewedJob` / `approveResult` 合约接口。本地启动器遇到旧合约会把原运行目录保存在 `.cache/demo-backups`，再部署支持人工确认的合约。Anvil 状态按秒保存在本机缓存，服务重启保留项目和待确认记录。团队使用外部链时必须部署新版合约并更新环境配置；本轮没有代替其他成员部署外部链。

## 安全提交与他人本地运行

通过 Git 或 GitHub Desktop 提交源码，不要把已安装的整个目录拖到 GitHub 网页。真实模型配置、`.env`、钱包私钥、访问令牌、数据库和本地链保留在本机；`.gitignore`、Docker 排除规则和源码打包检查分别保护 Git、容器和 ZIP。不要用 `git add -f` 强制添加私有文件。`.gitignore` 不能删除已经进入历史的秘密；若今后误提交真实密钥，应先在提供商撤销或轮换，再处理历史。

提交前执行 `python scripts/check_public_source.py`；暂存后执行 `python scripts/check_public_source.py --staged`。检查只显示文件名和规则，不输出密钥值，并阻止已暂存的私有文件和常见密钥格式。可运行 `git config --local core.hooksPath .githooks` 启用自动提交前检查（Linux 若提示 hook 不可执行，先运行 `chmod +x .githooks/pre-commit`）；新克隆者需要自行启用，Git 不会自动安装 hooks。GitHub Actions 也检查提交后的源码，作为补充；密钥应在本地提交前拦截。

他人按“首次安装与启动”恢复依赖，按“接入规划模型”填写自己的配置即可。本地钱包、访问令牌和链数据会独立生成，不需要也不应复制开发者的 `.cache`、`deployments` 或任何真实密钥。源码包仍可通过 `python manage.py package` 生成，在解压后的 `submission/src` 中执行安装和启动命令。源码包不包含 Git 元数据，直接运行不需要 Git 历史；生成新的源码包或使用 Git 提交检查时需要处于 Git 工作区。

## 构建与工程结构

安装依赖后，`python manage.py build` 重新编译合约和前端；`python manage.py schema` 将接口定义导出到忽略目录。首次运行 `manage.py` 默认启动本地服务。在团队已有链上部署时，按 `.env.example` 设置环境变量，再用 `configure` 和 `start` 启动。

```text
apps/web/                 React / TypeScript 控制台
```

## Anvil 状态持久化

默认 Anvil 已支持自动保存、重启加载、历史交易/回执和合约状态恢复。在启动窗口按 Q 或 Ctrl+C 会停止服务、保存并停止本项目的链；按 R 重启时保留链运行。单独管理链时可用 `python manage.py stop-chain` 停链、`python manage.py save-chain` 保存。下次仍用 `python manage.py dev` 或 start-demo.cmd 启动，无需日常重新部署。

如果上次的链端口被其他项目占用，启动器会自动换用空闲端口，加载本项目原有快照，核对合约后更新连接地址。不会接管或停止其他项目的链，也不会因此重新部署或清空任务记录。

每 5 秒生成自动快照，异常退出恢复到最后有效快照；未保存的最近操作可能丢失。旧内存链在功能启用前已经丢失的状态无法重建。快照、应用数据和账户配置都保存在 Git 忽略目录。详见 [Anvil 持久化与恢复](docs/anvil-persistence.md)。
