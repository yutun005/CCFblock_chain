# AgentFlow Pay 测试报告（Dmodule 集成验证）

## 1. 范围与结论

本报告记录 `Dmodule` 将 A 应用接到 C 的 DASC v1 合约接口后的验证情况。报告中的测试状态来自本分支实际执行结果；Cmodule 独立运行的结果不作为本分支端到端通过证据。

架构、业务流程、资金状态和信任边界说明见[设计报告](设计报告.md)。

当前 Dmodule 采用 C 合约的 `TaskConfig`、EIP-712 布尔 `verdict`、`paymentToken()`、`expireTask(jobId, taskId)`、钱包级 `withdraw()` 和 `withdrawRefund(jobId)`。A 的任务规划、调度、A2A、成果验证与页面保留。C 合约没有链上 `planHash` 和 `requestStop`：任务需求哈希在链上逐任务核对；停止后续委派是本地调度状态，已接受任务仍可完成。钱包级提款事件没有 `jobId`，不在页面分摊到单个 Job。

## 3. 测试数据与方法

集成接口检查使用仓库中的 C `TaskEscrow.sol` 和 A `app.py` / `web.tsx`；检查 Solidity 函数、任务配置 tuple 顺序、EIP-712 `verdict` 类型、后端调用名称及前端账本文案。该检查不需要外部 RPC 或密钥。

链上安全、正常端到端、恢复和旅游场景测试均由 Dmodule CI 实际运行。CI 归档包含 Foundry JSON、SEC 原始记录、E2E 快照/日志、汇总和交付包。本机 Playwright 使用路由 mock 完成浏览器交互 smoke；真实后端与浏览器联合验收、Docker 干净环境复现、随机状态 invariant 及性能对照仍未运行。本报告不推算或填写未采集的耗时、Gas 和性能收益。

## 6. 未解决项与失败样本

- 浏览器与真实后端联合验收、Docker/干净电脑部署复现、随机状态 invariant handler、性能对照尚未执行。已通过的 Playwright smoke 使用 API mock；CI Ubuntu runner 上的一键构建和链上 E2E 通过，但不能代替用户按部署说明在全新电脑手动复现。
- SEC-09、SEC-10、SEC-28、SEC-29 仍为 `SKIP`：分别缺少恶意服务端点完整联调、恶意能力 Agent 的链上拒付实验、恶意代币重入实验、服务重启后重复发送结算实验。SEC-30 是明确披露的验证者信任限制。
- 较早的 workflow run `38863309105` 在恢复场景失败：task 1 连续请求报价后返回 `NO_VALID_QUOTE`，导致恢复 Job 为 `PARTIAL_FAILED`。后续提交修正恢复时序；最新 run `38871130279` 的 10 次主场景和 1 次旅游场景均通过。失败原始记录仍保存在旧 run，不能用最新成功覆盖失败样本。
- CI artifact 中原始 `security-summary.csv` 因函数签名匹配错误把 29 项标为 `SKIP`。原始 `forge-results.json` 本身包含 27 个 `Success`。本地修复映射器后，直接重算该归档 JSON 得到 25 `PASS`、4 `SKIP`、1 `LIMITATION`；旧 artifact 的 CSV 未被改写。当前本机也重新执行了 27 项 Foundry 用例，得到相同的安全矩阵。
- 旧收集器同时读取批次摘要和逐次 `result.json`，把 CI 的 11 次实际 E2E 重复计为 22 行。本地收集器现按 `run_id` 去重，并校验重复来源的场景、状态、耗时和失败信息；旧 artifact 的汇总文件未被改写。旧 CI 原始批次仍是主场景 10 次与旅游场景 1 次，不能把 22 行解释为 22 次独立实验。
